# 全体制作計画

更新2026-11-14。調査基準日2026-10-26。対象はGitHub.comを使う開発経験者。今回の範囲はPhase 0〜2で、本文は未執筆。

## フェーズと完了条件

| Phase | 成果 | 完了条件 |
|---|---|---|
| 0 | リポジトリ・MkDocs・品質基準・CI | 固定依存でstrict build、台帳と内部リンク検証、Git保存 |
| 1 | Docs分類・機能台帳・出典台帳 | 選定資料の主張を出典へ結び、未巡回範囲と不明条件を記録 |
| 2 | UI Map・詳細目次・機能対応 | 50章の目標・前提・節・演習を設計。実UI確認は独立状態で記録 |
| 3 | 企業公開事例 | 公開日・課題・採用機能・成果・適用限界を根拠ごとに確認 |
| 4 | 章別本文 | 対象章の詳細仕様・条件・手順が確認済み。未検証は明示 |
| 5 | Labとテスト | 第三者再現、期待結果・失敗例・採点・片付け手順 |
| 6 | 品質レビュー | 出典・UI・実行・教育・網羅性を別観点で監査 |
| 7 | 統合・公開準備 | 検索・表示・リンク・build検証後、公開承認を得る |

Phase 1の全Docs走査とPhase 2の全権限UI照合は、選定調査と設計完成だけでは終了しない。[残課題](../research/research-gaps.md)と[監査](../audits/audit-report.md)を参照する。

## 章執筆前ゲート

1. [機能対応表](feature-chapter-map.md)から対象Feature IDを抽出する。
2. 機能概要、技術仕様、プラン、権限、public/private、正式状態の出典を確認する。
3. 基準日後の資料と日付なし現行Docsを区別し、Changelogと整合を確認する。
4. UI手順は観察日・plan・role・visibilityを記録する。実機なしは仕様説明または設計演習とする。
5. 演習の対象・変更範囲・必要費用・終了後の削除/停止を定義する。

最初の制作候補は第1章。Gitのオブジェクトと参照の理解が後続章の誤解を減らすため。第2・5・6・9章の不足調査を並行して行う。教材全50章を一括生成しない。

## 継続更新

毎週Changelogを確認し、重要変更はFeature ID・章・演習へ影響付けする。毎月Docs索引とUIを再照合し、未登録機能・改名・廃止を確認する。料金・AI・Previewは執筆直前に再確認する。

更新はresearch/fragmentsの原本→統合CSV→章対応→検証→PRの順。1章か独立調査単位でコミットし、進捗と根拠をリポジトリへ残す。クラウド環境の消失に備え、完成待ちでなく専用ブランチへ途中保存する。

main初期化pushは過去の自動承認レビューで拒否された。明示承認なく再試行しない。mainへのマージ、公開設定変更、有料導入、本番デプロイは承認が必要。
